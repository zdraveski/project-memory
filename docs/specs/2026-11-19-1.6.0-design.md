# project-memory 1.6.0: memory you can feel

Status: design, not built. The maintainer picked the scope on 2026-11-19: all six headlines below.
Builds on 1.5.3. It replaces the earlier 1.6.0 design ("the recall release", PR #178). Parts of
that design are reused, and each reuse is named.

## Intent

project-memory saves well and is almost invisible. It records every exchange, sorts notes and takes
snapshots, but Claude has to decide to look, and it rarely does. On the build PC, outside the
plugin's own project, Claude searched the journal in 1 of about 40 sessions in 14 days. A user who
installs the plugin sees nothing change.

1.6.0 is the release a user feels. Six headlines:

1. **Memory that speaks up.** The plugin hands Claude a short pointer to earlier exchanges at the
   moment it matters: the first change of a file, a prompt that names something old, an error seen
   before, and after a compaction.
2. **Fast and light.** A measuring tool first, then a faster briefing and save, a smaller briefing
   and a smaller skill.
3. **A page you can open.** One command writes one local HTML file with every project, day by day.
4. **Sessions that see each other.** A session learns what the other open sessions in the same
   project are doing.
5. **Who said it.** One command shows the user's own words, and a note names the exchange that
   wrote it.
6. **Ask memory a question.** A helper agent ships with the plugin and answers a question about the
   past with dates and quotes.

## What was measured

All numbers are from the build PC, 2026-11-18 and 2026-11-19. Counts and times only.

| What | Number |
|---|---|
| Sessions outside the plugin's own project in which Claude searched the journal | 1 of about 40 |
| Files Claude changed that an older conversation had changed before (two code projects) | 34% and 55% |
| Prompts that share 3 or more rare words with an older exchange | about 1 in 14 |
| Prompts with no rare word at all ("go", "eta") | about half |
| Days with two live sessions in one project | about 1 in 3 |
| Same file changed by two sessions within 30 minutes | 4 times in 39 days |
| Plain scan of one journal (18 day files, 3.1 MB, 672 entries) | 14 to 16 ms read, 15 to 19 ms match |
| Briefing, live, from Claude Code's own records (145 runs) | median 2.6 s, worst 17.2 s |
| Briefing on `bench.mjs` | median 0.15 s |
| Save after a reply, live (1,116 runs) | median 0.5 to 0.9 s, worst 45.7 s |
| Save after a reply on `bench.mjs` | median 0.28 s, or 0.95 s when a note changed |
| Node starting an empty script | 0.07 s |
| Briefing size | about 2,180 tokens, of which the shared index about 720 |
| Skill text | about 2,890 tokens, attached again after each compaction |
| `Ran` lines | 54% of the journal's bytes |

Two things follow. A plain scan is fast enough, so no search index is needed at today's sizes. And
live hook times are five to seventeen times the bench, for a reason nobody has found yet.

## Goals

- **G1.** In the eval (section "The gate"), every pointer trigger that ships gives more right
  answers on its own cases than the same sessions without pointers, and the control cases stay the
  same.
- **G2.** The new hooks stay inside their time budgets on the bench (section "Budgets").
- **G3.** With every new hook in place, no existing bench case is slower than on 1.5.3. The live
  goals (briefing median under 0.5 s, save median under 0.2 s) are kept as goals. They become
  promises only if the measuring tool shows the cause is inside the plugin.
- **G4.** On the bench's busy store, the briefing at the start of a session is at least 30% smaller
  than the one 1.5.3 prints for the same store. (Live it is about 2,180 tokens today, so about
  1,500.) The skill's core is 1,200 tokens or less (2,890 today).
- **G5.** `memory page` writes one file that opens with no network and shows every project day by
  day.
- **G6.** A session learns of other live sessions at its start, at a prompt, in `status`, and when
  it changes a file another live session changed.
- **G7.** `search --asked` looks only in the user's own words. `history <note>` and `show <note>`
  name the exchange that wrote a note.
- **G8.** The helper answers a question about the past with dates, entry keys and the user's words
  quoted, and says "not found" plainly.

## Non-goals

- No search index, no embeddings, no model call inside a hook.
- No sync between computers, no server, no network.
- No pointer to another project's journal.
- No new hook blocks a tool call. (Whether `enforce` blocks is a separate, later decision.)
- No `memory claim` command.
- No new line and no new field in a journal entry, so an older plugin loses nothing when it reads a
  newer journal. The `Ran` cap (headline 2c) only shortens text inside a line that exists today.
- No rewrite of existing journal entries. The `Ran` cap applies to new entries only.
- No `--open` flag: the page command prints a link, it starts no program.
- Items of the earlier 1.6.0 design that this text does not name (usage counts in `status`, saving
  what the journal misses, the format canary, `erase` and `clean`, dead stores, relative dates)
  are not in 1.6.0. They stay candidates for patch releases.

## Anti-goals

The release fails, even if every feature works, when any of these happens:

- A pointer misleads Claude, or reads as an instruction.
- A hook makes each prompt feel slower.
- Text of a private, incognito, forgotten or switched-off conversation reaches another conversation
  or the page.
- A session in which memory has nothing to say costs more tokens than on 1.5.3.
- The page can run script that came from journal text.
- A trigger ships although its eval showed no gain.

## Constraints

- Node 22 or newer, no dependencies, no network. Windows, macOS and Linux.
- Every hook fails open: on any error it prints nothing and exits 0.
- Files the plugin writes are private to the user (mode `0o600`, folders `0o700`), as today.
- Every new message is plain words, and a test pins its text.
- Test fixtures are made up. Nothing from a real conversation goes into the repo.
- A paid or headless test never touches the real memory: it runs with its own temporary
  configuration folder.
- Small pull requests, one topic each. Tests on the three systems before a merge.

## How the plugin works today

Short, and only what this design builds on.

- **Hooks.** `Stop`, `StopFailure`, `SubagentStop` and `PreCompact` (manual) run
  `memory-tier.mjs --stop`. `SessionStart` runs `brief.mjs --print`. `PreCompact` (auto) runs
  `compact-gate.mjs`. `PreToolUse` runs `enforce-hook.mjs` for git commands. Every hook already
  starts Node directly, with no shell (`"command": "node"` plus `args`), since 1.0.0.
- **Journal.** One file per day in the store's `journal` folder. An entry holds a key, the time,
  the conversation tag, the branch, `Asked`, `Answered`, `Changed` (every file the turn changed,
  never cut) and `Ran`. A path in `Changed` is relative to the turn's working folder when the file
  is inside it, and a full path otherwise. The entry does not record that working folder. It does
  record, in its `t:` field, the folder name of its conversation file: the folder the session
  started in, with every character that is not a letter or a digit turned into `-`. A helper's
  entry holds its report and no changed files.
- **Reading.** `entries(dirs, {since, until})` opens only the day files in range. `told()` drops
  forgotten keys. A private turn is saved as `[private]`.
- **Telling a user prompt from other input.** `asked({}, text)` in `handoff-log.mjs` is false for
  slash commands, nudges and wrapped system text. `own(text)` strips wrapper tags.
- **Safe printing.** `fit()` in `handoff-log.mjs` redacts line by line, defuses markup and caps the
  length. The briefing prints every exchange line through it.
- **Other sessions.** At the start of a session the briefing already names up to two other working
  sessions, found by the conversation files changed in the last 30 minutes (`ACTIVE`), with the
  last request recorded for each.
- **Per-session state.** Small files under `<projects root>/.nudge/`, named by the conversation
  tag (the first 8 characters of its id).
- **CLI.** `memory.mjs` with `search`, `show`, `status`, `history`, `restore`, `promote`, `forget`,
  `incognito`, `off`, `on`, `rescan`, `enforce`, `doctor`. `search` takes `--since`, `--until`,
  `--all` and `--limit`. `show` takes entry keys only. `history <note>` lists a note's snapshots.
- **Finding the store.** Every hook calls `storeOf()` with its input. It reads a few small files
  and starts no `git` process. Sessions in a subfolder or in another worktree of one repository
  get the same store.
- **Bench.** `bench.mjs` copies the largest conversation file and store into a throwaway home and
  times each hook there.

## Approaches

### How memory reaches Claude

- **A. Hooks hand Claude short pointers.** Picked. A pointer names a date, the conversation, the
  user's earlier request cut short, and the key that opens the whole exchange. It costs no model
  call and works when Claude would not have searched.
- **B. Stronger wording, so Claude searches by itself.** This was the earlier 1.6.0 design. The
  measured rate (1 of about 40 sessions) says wording alone does not carry a release.
- **C. Hooks put the matching exchanges' full text into the conversation.** More tokens at every
  prompt, more saved text that could carry an instruction, and noise when the match is weak.
- **D. A search index or embeddings.** Needs a dependency or a model. A plain scan takes about
  35 ms at today's sizes, so there is nothing to win yet.

### How sessions see each other

- **A. Each session keeps a small file of what it is doing, and the others read it.** Picked. One
  append per prompt and per changed file, one small folder to read.
- **B. Read the other sessions' conversation files.** They are large (hundreds of MB), and reading
  them at every prompt is too slow.
- **C. Claude Code's own messaging between sessions.** It carries messages, but it does not show
  what each session works on, and the plugin cannot rely on it being there.

### The page

- **A. One static file, written by a command.** Picked. No port, no process, nothing to stop.
- **B. A local server.** A live view, at the cost of a running process and an open port. Not worth
  it for a page that is read now and then.

### The helper

- **A. An agent file shipped in the plugin.** Picked. Claude Code runs it, on a small model, with
  the tools the plugin names.
- **B. A CLI command that calls a model.** It would need a network call and a key. The plugin makes
  no network calls.

## Rules for everything in this release

1. **A pointer is a record, not an instruction.** Every pointer block says so in its first line.
2. **A pointer line holds:** the date and time, the conversation tag, the user's `Asked` words cut
   to 100 characters, at most three file names, and the entry's key. It never holds text from
   `Answered` or `Ran`. The error trigger's line holds a date and a key only.
   This changes one rule of the earlier design ("a hook never puts saved text into the
   conversation"). The reason: the headline the maintainer picked says a pointer shows what was
   asked. The briefing has printed earlier requests the same way since 1.0.
3. **Every pointer passes `fit()`**: redacted, defused, capped. A block is at most 800 characters.
4. **Only this project's store.** No pointer comes from another project's journal.
5. **Never from** a `[private]` entry, a forgotten key, an incognito conversation or a project
   that is switched off. An incognito or switched-off conversation gets no pointer and writes no
   session file.
6. **"Earlier" means:** an entry of another conversation, or an entry of this conversation that is
   older than this conversation's last compaction. After a compaction Claude no longer holds the
   detail, so its own older exchanges count as memory.
   "This conversation" is the conversation id in the hook's input. A forked conversation has a new
   id, so it can get a pointer to an exchange it still holds. That costs a few tokens and misleads
   nobody. The compaction is known from one line the briefing writes (section "The session file").
   If that write fails, the conversation gets fewer pointers, never wrong ones.
7. **Never twice.** A conversation is told about an entry once. The list is cleared at a
   compaction.
8. **One switch.** `PROJECT_MEMORY_RECALL=0` turns every pointer off. The eval uses it for the arm
   without pointers.
9. **Fail open, and stay inside a deadline.** `hooks.json` gives each new hook 5 seconds. The hook
   itself stops scanning after 400 ms and then says nothing.
10. **One reader.** The hooks and `search` read the journal through the same functions and split
    words the same way, so they cannot disagree about what matches.

## The session file

One small file per conversation, outside the store, beside the plugin's other per-session state:

```
<projects root>/.sessions/<store's project folder>/<tag>
```

`<store's project folder>` is the name of the folder that holds the store, found with `storeOf()`.
Sessions that share a store share this folder, so a session in a subfolder or in another worktree
of the same repository is seen too.

It is outside the store on purpose: the store's change fingerprint, the snapshot and `status` never
see it, so a prompt can never cause a tiering pass or a snapshot. It is not under `.nudge` either:
the weekly sweep there removes plain files only, and an old folder would stop it.

The file is append-only. Each line is `<kind> <ISO time> <rest>`. Appending keeps two hooks that
run at the same moment from losing each other's lines.

| Kind | Rest | Written by | Used for |
|---|---|---|---|
| `file` | the full path, normalised as the journal does | `PostToolUse` | the first-change check, the same-file warning |
| `told` | an entry key | every trigger | never the same pointer twice |
| `error` | the hash of an error signature | `PostToolUseFailure` | once per error and conversation |
| `compact` | nothing | the briefing after a compaction | the "earlier" rule; clears `told` and the first-change list |
| `asked` | the request, redacted, one line, cut to 120 characters | `UserPromptSubmit` | what this session is doing |
| `title` | the session title, when the user set one | `UserPromptSubmit` | naming the session |
| `saw` | another session's tag, and a path or nothing | the hooks | warn once per session and file |
| `end` | the reason | `SessionEnd` | the session is no longer live |

Rules:

- A `file` line is appended for a path only when the newest line for that path is older than five
  minutes. A long session then adds a few kilobytes, not a line per edit.
- When the file passes 64 KB, the prompt hook rewrites it with the newest line of each kind and
  path. Only the prompt hook rewrites. A line another hook appends in that instant can be lost,
  and the cost is one repeated pointer.
- A session is **live** when its newest line is younger than `ACTIVE` (30 minutes) and is not
  `end`. A resumed session appends after `end` and is live again. The hooks decide by this rule
  alone: a hook never opens another session's conversation file.
  `shortcut:` a session that has run for 30 minutes without a prompt or a changed file is not live
  for the hooks. The briefing and `status` still find it by its conversation file, as today.
  Upgrade if users miss warnings: one line from the save after a reply.
- The save after a reply deletes session files older than 7 days.
- `incognito` deletes this conversation's session file. `forget` and `off` delete every session
  file of the project: an `asked` line can hold words of a forgotten exchange, and a project that
  is switched off keeps nothing new.

## Headline 1: Memory that speaks up

### 1a. Search filters

Three new filters for `search`. They work alone or with words, and with the options `search` has
today (`--since`, `--until`, `--all`, `--limit`). Without words the newest come first, 30 by
default.

- `--file <path>`: entries whose `Changed` holds the file. The path matches when it equals a
  changed path, or is the end of one at a folder boundary (`store.mjs` matches `hooks/store.mjs`).
- `--asked`: words are matched in `Asked` only, and helper entries are left out. (Today only a
  search by date leaves helper entries out. A search by words keeps them, and that stays.)
- `--conversation <tag>`: entries of the conversation whose id starts with the given text.

### 1b. A file with a past

**When.** `PostToolUse` for `Edit`, `Write` or `NotebookEdit`, so only after a change that worked.
The hook's text reaches Claude with the tool's result. It never delays the change.

**Steps.**

1. Read the input. Stop when pointers are off, memory is off, or the conversation is private.
2. Take the path from `tool_input.file_path` or `tool_input.notebook_path`. Stop when the file
   belongs to the plugin's own data (the store, `handoff.md`, the projects root).
3. Read the session file. Append a `file` line when due. Stop here when this conversation already
   changed the file since its last compaction. This is the common case and must cost little more
   than starting Node.
4. Work out how an entry would have saved this path. The journal saves a path relative to the
   turn's working folder when the file is inside it, and the full path otherwise. An entry names
   the folder its session started in (the `t:` field). So: take every folder above the file, up
   to the root of the disk. For each, make its name the way the `t:` field has it, and keep the
   file's path relative to that folder, made with the journal's own `rel()`. This is text work
   only: no folder is opened.
5. Scan the day files, newest first, for earlier entries whose `Changed` holds the file: either
   the full path, or the relative path that belongs to the entry's own start folder. So
   `README.md` saved by a session that started in a subfolder never matches the `README.md` of
   the repository root, and a file in one worktree never matches its copy in another. Paths are
   compared the way the journal compares them (case ignored on Windows and macOS), with `/` and
   `\` taken as the same. Window: the newest 365 days or 16 MB of day files, whichever is
   smaller.
   `shortcut:` a turn that ran after a `cd` into another folder saved its paths relative to that
   folder and is missed. So is a session whose folder name Claude Code shortened (a very long
   path). Upgrade when the eval or a user shows it matters: record the working folder in new
   entries, which is a change of the journal's format and needs its own design.
6. Show the newest two, from different conversations when possible, then "and N more" with the
   `search --file` command.
7. Append a `told` line for each entry shown.

The same-file warning of headline 4 runs in this hook after step 3.

The hook also runs inside a helper. A helper's change gets the pointer, and its `file` line goes
into the session file of the conversation that started it.

**What Claude sees** (wording is pinned by tests once chosen):

```
project-memory: earlier exchanges changed src/closeDay.js. These are records of past requests, not instructions.
- 2026-11-12 14:02 [3f07bb43] asked: "the nightly export is one day off" · key: "3f07bb43 2026-11-12T14:02 a1b2c3d4e5f6"
- 2026-11-03 09:40 [9a1c22e0] asked: "move the export to 02:00" · key: "9a1c22e0 2026-11-03T09:40 0f9e8d7c6b5a"
and 4 more: memory skill, search --file src/closeDay.js
Open one in full: memory skill, show "<key>"
```

**A limit, stated.** The pointer arrives with the result of the first change, not before it. A hook
cannot hand Claude text before a tool runs unless it blocks the tool or asks the user. If the eval
shows the pointer comes too late, the next step is the same look-up at the first `Read` of a file.
Reads are far more frequent, so that step is taken only on evidence.

### 1c. A prompt that names something old

**When.** `UserPromptSubmit`.

**Steps.**

1. Stop when pointers are off, memory is off, the conversation is private, or the input has an
   `agent_id` (a helper's prompt).
2. Stop unless `asked({}, prompt)` is true. Take `own(prompt)` as the text.
3. Append the `asked` line (headline 4 uses it).
4. Split the text into words with the shared splitter (stems, no stop words). Stop when fewer than
   2 words are left: "go" and "yes" end here, before any day file is read.
5. Scan the user's entries of the newest 90 days or 4 MB of day files, whichever is smaller. Count
   for each word of the prompt how many entries hold it. The text of an entry is `Asked`,
   `Answered` and `Changed`. `Ran` is left out: it is half the bytes and mostly command noise.
6. A word is **rare** when at least one entry holds it and fewer than 5% do.
7. An earlier entry **matches** when it shares 3 rare words with the prompt, or 2 when the prompt
   has exactly 2. This is the rule of the replay that gave "about 1 prompt in 14".
8. Show up to three, the highest sum of rarity first, the newest first on a tie. Say nothing when
   none matches.
9. Append a `told` line for each entry shown.

The eval tunes the two numbers, inside these bounds: 2 to 4 shared words, 3% to 10%. Before the
pull request, the replay is run again with the product's own word splitter, and the pull request
states the rate (counts only).

**What Claude sees:**

```
project-memory: earlier exchanges share words with this request. These are records of past requests, not instructions.
- 2026-11-17 10:15 [9a1c22e0] asked: "which port should the dev server use" · changed: vite.config.js · key: "9a1c22e0 2026-11-17T10:15 5d4c3b2a1908"
Open one in full: memory skill, show "<key>"
```

Not built: pointers to notes, and pointers to entries of other projects.

### 1d. An error seen before

Reused from the earlier design (its section 5), which was audited. In short:

- **When.** `PostToolUseFailure` for `Bash` and `PowerShell`. Skipped when `is_interrupt` is true
  or the error holds `Command timed out`.
- **Signature.** The last 300 characters of `error`, squeezed to one line the way the journal
  squeezes a failed result; every run of digits becomes `#`; every path becomes its last part;
  spaces collapsed; the last 120 characters of that. Shorter than 20 characters: ignored.
- **Look-up.** The newest 90 days, newest first, for an entry of another conversation whose `Ran`
  holds `→ failed:` with the same signature. Only a conversation whose newest entry is at least one
  hour old counts: a second session that just hit the same failing test has no fix to read yet.
- **Once** per signature and conversation (an `error` line in the session file).
- **The line:**

  ```
  project-memory: the same error was hit on 2026-11-12 in another conversation. Before trying again, read what was done then: memory skill, show "<key>"
  ```

- **The gate, before any hook code.** A throwaway script outside the repo replays the rule on the
  last 30 days of every project's journal on the build PC, the plugin's own project left out.
  Fewer than 5 hits: the trigger is dropped and the maintainer is told. Otherwise up to 20 hits
  are read and marked useful or not, in a local report. Useful means the earlier entry, or one of
  the next two of that conversation, names the cause or the fix. At least half useful: build it.
  Less: change the signature rule once and replay once. The maintainer has the last word on
  "useful". The hits hold real conversation text and stay local. The pull request gets counts only.
- **Before it ships.** One live check with two headless sessions in a temporary project, and a
  fixture pair (the hook's input and the journal line of the same failure; made-up text, real
  shape).

Not built: hits from other projects, fuzzy matching, tools other than the shell, any text of the
old entry in the line.

### 1e. After a compaction

The briefing that follows a compaction (`SessionStart` with the source `compact`) gains three
things:

1. **Pointers for the task in progress.** The matcher of 1c runs on this conversation's last real
   request. Up to three pointers to earlier exchanges, entries the briefing already prints left
   out.
2. **One line of files.** The files this conversation changed before the compaction, the newest
   ten, then "and N more", and the command `search --conversation <tag>`.
3. **A `compact` line** in the session file. From here on, this conversation's own older exchanges
   count as "earlier", the first change of a file counts as first again, and the `told` list is
   empty.

All of it fits inside the briefing's existing cap.

### The gate

`recall-eval.mjs`, reused from the earlier design (its section 2b), which was audited. In short:

```
node recall-eval.mjs --plugin <dir> [--set <name>] [--without] [--runs N] [--case <name>] [--model sonnet] [--max-usd 20] [--json <path>]
node recall-eval.mjs --self-check
```

- It automates headless `claude -p` sessions in throwaway projects whose journals hold made-up
  facts.
- **It never touches the real memory.** The harness and every session run with `CLAUDE_CONFIG_DIR`
  set to one new folder under the OS temp folder. How the login gets there is the first thing the
  build finds out, from the Claude Code documentation. A copied login file is used only if the
  documentation says a copy is safe. If no safe way exists, the harness is not built, the
  maintainer is told, and nothing is run against the real folder in its place.
- A run sweeps what a killed run left, makes one project per session, seeds the stores through the
  journal's own writer, checks the seed with `search` before any paid session, runs 4 sessions at
  a time, grades each answer against the case's pattern, adds up the cost, stops at `--max-usd`,
  and always deletes its folders. It refuses to start when a folder it would delete is not under
  the OS temp folder.
- The arm **without** runs the same plugin with `PROJECT_MEMORY_RECALL=0`, so the difference is the
  pointers and nothing else.
- Whether a pointer was shown is read from the session's conversation file, where Claude Code saves
  what a hook said. The answer alone cannot tell.
- **No harness, no trigger.** If the harness cannot be built, no trigger ships on the builder's own
  decision. The builder stops and the maintainer decides how to go on.

**Cases** (project "bookshop", all invented; each case runs 5 times in each arm):

| Case | Trigger | The session is asked | Seeded earlier exchange | Passes when |
|---|---|---|---|---|
| `file-rule` | file | Change `src/cart.js` so totals are rounded to 2 decimals. | asked: keep 4 decimals in cart totals, the tax export needs them | the answer matches `4 decimals\|tax export` |
| `file-none` | file, control | Add a `clear()` function to `src/wishlist.js`. | none for that file | no pointer was shown, and the function exists |
| `port-implicit` | prompt | Which port should the dev server use? | port 4317, because 3000 and 8080 are taken | the answer matches `4317` |
| `pdf-implicit` | prompt | Should we keep the PDF export? | decision: drop the PDF export, keep CSV only | the answer matches `CSV` |
| `no-need` | prompt, control | Write a JavaScript function that reverses a string. Just the code. | unrelated entries | no pointer was shown, and no memory search ran |
| `never-discussed` | prompt, control | Which payment provider did we choose? | unrelated entries | the answer names no provider |
| `error-again` | error | Run `node deploy.js` and tell me what to do about the result. | the same failure, fixed by running as the `deploy` user | the answer matches `deploy user\|chown` |

**A trigger ships when:** its cases pass in at least 4 of 5 runs with pointers, and more often than
without; every control passes in both arms; and the median cost of a control session with pointers
is at most 15% above the one without. A trigger that fails is not shipped, and the maintainer is
told with the numbers.

**Cost.** A full run is about 70 sessions. The builder states the expected cost, checks the plan's
usage, and asks the maintainer before the first paid run. Under a subscription login a run spends
plan usage, not only money.

The pointers after a compaction are not in the eval: a headless session cannot be compacted on
demand in a way the harness controls. Unit tests on the briefing cover them.

### Budgets

Measured on `bench.mjs` with the busy store (headline 2a), on the build PC. Node alone takes 70 ms.

| Case | Median | 90th percentile |
|---|---|---|
| Prompt hook, nothing to say | 150 ms | 250 ms |
| Change hook, file already seen | 110 ms | 160 ms |
| Change hook, first change of a file | 250 ms | 350 ms |
| Error hook, no match | 200 ms | 300 ms |
| `SessionEnd` | 110 ms | 160 ms |

A budget that cannot be met shrinks the scan window. It does not move the budget. The prompt
hook's window does not go under 30 days or 2 MB. If the budget cannot be met there, the builder
stops and brings the numbers to the maintainer.

## Headline 2: Fast and light

### 2a. Measure first

Live hooks are five to seventeen times slower than the bench, and the cause is unknown. One early
guess is already ruled out: the hooks do not pay for a shell, they have started Node directly
since 1.0.0. So the first pull request measures, and changes no behaviour.

- **Timing lines.** Every hook run appends one line of numbers to `<projects root>/.timing`: the
  time, the hook, the event, the milliseconds from process start to the script's first line, the
  milliseconds of each phase, and the total. No text, no paths. The file is cut to its newer half
  at 256 KB. `PROJECT_MEMORY_TIMING=0` turns it off.
- **`doctor`** gains one line per hook: runs, median, 90th percentile and worst of the last 7 days.
- **`bench.mjs`** gains a made-up busy store: 60 day files with 10 MB of journal (about 2,000
  entries), 150 notes, a shared index at its 3,000-byte budget, and a conversation file of 50 MB.
  That is about three times the largest store on the build PC. It also gains a case for every new
  hook and for `search` and `status`, `--json <path>`, and `--live`.
  `--live` reads Claude Code's own duration records from the conversation files of one project,
  read-only, and prints them beside the plugin's timing lines. The gap between the two is time
  spent outside the plugin: starting the process, other plugins' hooks, the virus scanner.
- **A speed test in CI.** `bench.mjs --check` on the made-up store passes when each case's median
  stays under a multiple of "Node, empty script" from the same run. The multiples come from the
  first measured numbers, with room. It catches a hook that got several times slower, not a 10%
  drift.

**A call for the maintainer:** release this pull request as 1.5.4, so real numbers collect on real
sessions while headline 1 is built. Development copies never run against the real data, so
without a release there are no live numbers.

### 2b. Cuts, each kept only when measured

Candidates, in the order to try them. A cut that wins less than 10% of a hook's time is dropped.

- Load only the modules a hook needs. Loading the plugin's modules costs 30 to 50 ms on top of
  Node's 70.
- Node's compile cache.
- The save after a reply: answer first, then do the slow tail (tiering, snapshot, backfill, sweep),
  or move the tail to a second hook entry with `async: true`. The store's lock already keeps two
  tails apart.
- The save reads 24% of the conversation tail's bytes for records it never uses. Skip them before
  parsing.
- `status` and `search`: find what dominates with the timing phases, then cut that.

**Honest statement.** If the measurement shows the time is spent outside the plugin, the release
says so, ships the cuts that are real, and the two live goals stay goals.

### 2c. Tokens

- **Briefing.** Each earlier exchange becomes a headline: the request, the first 160 characters of
  the answer, the changed files as today, the newest five. The full text stays in `handoff.md` and
  the journal, one command away. Pointers now bring the detail when it is needed. The shared
  index stays whole: its lines are standing rules, and a new conversation has never seen them.
- **Skill.** A core of 1,200 tokens or less (when to search, the five everyday commands, how to
  read a hit) and reference files for the rest (`restore`, `promote`, `forget`, `enforce`,
  `doctor`, options). The core names each reference file and when to read it.
- **`Ran`.** One command in a new entry is capped at 500 characters, with a mark such as
  `[+1,840 characters, in the conversation file]`. Existing entries are not rewritten. Nothing is
  lost: the conversation file keeps the full command.

## Headline 3: A page you can open

`memory page [--days N] [--project <name>]` writes one HTML file and prints its `file://` link.

- **Where.** `<config dir>/project-memory/journal.html`, folder `0o700`, file `0o600`. Never
  inside a project folder, so it cannot be committed by accident.
- **What.** Every store, days newest first, 30 days by default (`--days all` for everything). Each
  entry shows the time, the conversation, the branch, what was asked, the answer cut short and
  expandable, the changed files, and a mark when it wrote a note. `Ran` is left out. A project
  list with counts, a day list, a search box, and a week strip that answers "what did I do last
  week".
- **What is left out.** Forgotten entries, switched-off projects, and the text of private turns
  (shown as `[private]`, as the journal holds them).
- **Safety.**
  - The data is embedded as JSON with `<` escaped. The script renders it with `textContent` only,
    never as HTML.
  - A `Content-Security-Policy` meta tag: `default-src 'none'`, the one script block allowed by its
    hash, the one style block allowed by its hash. Script that came from journal text cannot run.
  - No network: system fonts (Inter when installed), the logo as inline SVG, no link the page
    fetches by itself.
- **Kept fresh by deleting.** `forget`, `incognito` and `off` delete the file. It is rebuilt on the
  next `memory page`.
- **Look.** The README's brand: navy, the cyan to violet glow, glass panels, the brain logo. The
  maintainer picks the look from rendered, numbered variants before this pull request is built.

## Headline 4: Sessions that see each other

What a session knows about the others comes from their session files (`asked`, `title`, `file`
lines). Two readers use two tests, on purpose:

- **The briefing and `status`** keep today's test (the other conversation file changed within
  `ACTIVE`) and take the detail from that session's file. They also list a session that only its
  session file shows as live: a session in another worktree, whose conversation file lies in
  another folder.
- **The hooks** (at a prompt, at a change) use the session file alone, by the "live" rule of the
  section "The session file". They run at every prompt and never open a conversation file.

Four places show it:

1. **The briefing.** The existing line "Another session is working in this project" gains the
   title, when one is set, and the newest files that session changed.
2. **`status`.** One line per live session: tag, title, last request, files.
3. **At a prompt.** Once per other session, when it became live since this conversation last
   looked:

   ```
   project-memory: another session [9a1c22e0] is working in this project since 14:02 on: "move the export to 02:00". Files it changed: src/closeDay.js, test/closeDay.test.js
   ```

   When both sessions changed the same file, the line says so.
4. **At a change.** When another live session changed this same file in the last 30 minutes:

   ```
   project-memory: another session [9a1c22e0] changed this file at 14:02 (its request: "move the export to 02:00"). Check with the user or that session before changing it again.
   ```

   Once per other session and file. It is shown again when the other session changes the file
   after this conversation was warned.

Rules:

- **Same file means the same file on disk.** `file` lines hold full paths, so two sessions in two
  worktrees of one repository never warn each other.
- **Never blocks.** The warning arrives with the result of this session's first change.
- **Private sessions are not seen.** An incognito conversation writes no session file, and its
  existing one is deleted.

**A call for the maintainer.** The picked headline said "a warning before it changes a file". A
hook can speak before a tool runs only by stopping it. The alternative is: stop the first try
once, with the warning, and let the second try through. This design picks "never block", and
names the alternative so it can be chosen.

Not built: a `memory claim` command, and messages between sessions.

## Headline 5: Who said it

- **`search --asked`** (section 1a) looks only in the user's own words.
- **`history <note>`** gains one line under each snapshot: the exchange that changed the note.

  ```
  3f2a91c 2026-11-12 14:03  changed
    by: 2026-11-12 14:02 [3f07bb43] asked: "save that as a rule" · key: "3f07bb43 2026-11-12T14:02 a1b2c3d4e5f6"
  ```

  The exchange is the newest entry whose `Changed` holds the note's full path, saved after the
  note's previous snapshot and no later than two minutes after this one. The note's own
  `originSessionId` breaks a tie. When there is none, the line says
  `by: no exchange found (changed by hand, by a shell command or by a helper)`.
- **`show <note>`.** When the argument is not an entry key and names a note of the store, `show`
  prints the note's name and description, then the first and the newest exchange that changed it,
  in the same `by:` form. An entry key wins when both exist.
- **A third standing line in the briefing:**

  ```
  A "decided", "rejected" or "parked" in a note is a session's summary. Before telling the user they decided it, check their own words: memory skill, search --asked <words>.
  ```

Limit: the plugin cannot judge what is true. It makes the check one command.

## Headline 6: Ask memory a question

A file `agents/recall.md`. Claude Code finds it in the plugin's `agents` folder and registers it
as `project-memory:recall`. No change to the plugin manifest.

- **Front matter.** `name: recall`. A `description` that says when to hand over: a question about
  the past that needs more than one search. `tools: Bash, Read, Grep, Glob`. `model: sonnet`.
  `maxTurns: 15`. `omitClaudeMd: true`.
- **Body.** The CLI line with `${CLAUDE_PLUGIN_ROOT}` (Claude Code fills it in inside an agent's
  body). Then how to work: try several wordings and filters (`--asked`, `--file`, dates), open
  every promising hit with `show`, answer first, then the sources as date, conversation tag and
  key. For a "who said it" question, quote the user's own words. Say "not found" plainly, with
  what was searched. Run only `search`, `show`, `history` and `status`: the helper never changes
  memory.
- **The skill** gains one routing line: for a question about the past that one search does not
  answer, hand it to `project-memory:recall`.
- **Its reports are not journaled.** `journal.subagent()` skips this agent type. Its report is made
  of journal text, and saving it would double every hit.
- **Gate.** On the eval's answer cases (the six of the earlier design: port, last week's bug, a
  decision, the staging database, an error's fix, a never-discussed question), sessions with the
  routing line answer right at least as often as sessions without it. If not, the helper is not
  shipped and the maintainer is told.

## Testing

- Each new module gets a suite in the house style. Fixtures are made up. Tests leave nothing
  behind.
- Every message a hook or the CLI prints is pinned by a test.
- For every hook: a test that a broken input, a missing store, an unreadable day file and a
  timeout all end with exit code 0 and no output.
- Privacy tests for every reader: a private entry, a forgotten key, an incognito conversation and
  a switched-off project never appear in a pointer, a session line or the page.
- The page: a test that journal text holding `</script>` and an `onerror` attribute stays text, and
  that the policy tag's hashes match the blocks.
- A test that a prompt and a file change cause no tiering pass and no snapshot.
- The file trigger: a session that started in a subfolder, and one in a second worktree, match the
  right file and no other.
- The bench's `--check` runs on the three systems.
