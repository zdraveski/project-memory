# 1.6.0 Step 1: Measuring (release 1.5.4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show where a hook's time goes, live and on the bench, without changing what any hook does: a reader of Claude Code's own hook durations, one line of numbers per hook run, the times in `doctor`, a made-up busy store for the bench, and a speed test in CI.

**Architecture:** Two small new modules and one grown tool. `timing.mjs` (shipped) collects marks inside a hook run and appends one JSON line to `<projects root>/.timing`. `live-times.mjs` (developer tool) reads the duration records Claude Code writes into conversation files. `bench.mjs` gains flags, a made-up store built by `bench-store.mjs`, more cases and a `--check` mode. `doctor` reads `.timing` through `timing.mjs`.

**Tech Stack:** Node.js 22+ ES modules, `node:perf_hooks` (the global `performance`), `node:fs`, `node:readline`, `node:child_process`; GitHub Actions.

**Spec:** `docs/specs/2026-11-19-1.6.0-design.md`, sections "What was measured", "Budgets", "2a. Measure first", "Build order" step 1, "Testing". Approved by the maintainer on 2026-11-20. This plan covers build step 1 and the release of 1.5.4. On 2026-11-20 the maintainer said the measuring tool is not released alone, so release 1.5.4 also holds build steps 2, 10 and 13 (the search filters, who said it, the page). Their plans lie beside this one. Order: pull requests A, B and C of this plan, then the plans for steps 2, 10 and 13, then pull request D below.

## Global Constraints

- Node 22 or newer, no dependencies, no network. Windows, macOS and Linux.
- **No hook changes what it prints, what it saves or its exit code.** This step measures. A test pins it for every hook entry (Task 3).
- Every hook fails open: on any error it prints nothing more and exits as it did before. The timing code never throws into a hook and never creates a folder.
- Files the plugin writes are private to the user: mode `0o600`.
- The timing file holds numbers and fixed names only. No text from a conversation, no path, no command.
- Every new message is plain words, and a test pins its text.
- Test fixtures are made up. Nothing from a real conversation goes into the repo, a commit message or a pull request. From real data only counts and times are reported, and other plugins' scripts are counted, never named.
- A development copy never writes to the real data. `--live` and `--real` read it, read-only.
- Test first. `node check.mjs` green before every commit. One change a commit. Stage files by name, never `git add -A`.
- Every commit is signed off (`git commit -s`, the `dco` check) and its message ends with the session's `Co-Authored-By` line. Write commit messages and scripts to files (Bash heredocs mangle backslashes on the build PC).
- Branch from `master`. Line numbers in this plan are those of 1.5.3 (commit 366c983): confirm each before editing.
- No mutant or fuzz run on GitHub's machines unless the maintainer says "run". The normal test workflow starts by itself on a push.
- No merge without the maintainer's "merge". Stack the pull requests and keep building. Before a parent merges with `--delete-branch`, retarget its child to `master`.
- Wait for a workflow run with `gh run watch`, not a hand-written loop.

## Decisions this plan makes (beyond the spec)

- **Three pull requests and a release, not one.** A: `--live` (a developer tool, reported at once). B: the timing lines, `doctor` and the documents (shipped code, with `PRIVACY.md` in the same pull request, as the spec demands). C: the bench. D: release 1.5.4. The spec says one pull request. The maintainer's standing rule is one topic per pull request, and A must exist before the rest anyway.
- **The line is JSON**, like `.stop-ran`: `{"t":1763590000000,"h":"save","e":"Stop","node":41,"start":88,"p":{"input":2,"load":35},"ms":312}`. `t` is `Date.now()` at the end. `node` is the milliseconds until Node finished starting. `start` is the milliseconds from process start to the hook's first line. `p` holds each phase. `ms` is the total, from process start to the write. All whole numbers.
- **Time zero is Node's own start** (`performance.now()` counts from it). What the operating system and Claude Code spend before Node runs is not in the line. `--live` shows it as the gap.
- **`h` is one of four fixed names:** `save` (`memory-tier.mjs --stop`), `brief` (`brief.mjs`), `enforce` (`enforce-hook.mjs`), `gate` (`compact-gate.mjs`). **`e` is the event name from the hook's input, kept only when it is letters**, with `:startup`, `:compact`, `:auto` and the like after it for `SessionStart` and `PreCompact`.
- **`brief.mjs` and `enforce-hook.mjs` load `timing.mjs` inside a `try`**, so a broken or missing `timing.mjs` cannot stop the briefing or the rule check. `memory-tier.mjs`, `handoff-log.mjs` and `compact-gate.mjs` import it statically, as they import `store.mjs`.
- **`timing.mjs` has no static import of a plugin module.** It loads `store.mjs` inside `flush()`, when every hook has loaded it already. Loading `timing.mjs` first then costs nothing a hook would notice.
- **`doctor` says "since <date>"**, not "in 7 days". The file is cut at 256 KB, which a busy user fills in fewer than 7 days. The date is the later of 7 days ago and the oldest line.
- **The CLI writes no timing line.** `search` and `status` get bench cases here. Their phases come with step 8, which cuts them.
- **The bench's default store becomes the made-up one.** Today's mode, a copy of the machine's largest store, stays as `--real`.
- **Left for later steps:** the 40 session files in the bench store and the pointer and `show` counts (step 4, when their format ships), and a bench case per new hook (each hook's own step). `SubagentStop` gets no case.
- **The `.stop-ran` code in `memory-tier.mjs:720-740` is not moved onto the new cut helper.** It is pinned by mutants, and this step changes no behaviour.

## Review Focus

1. Two sessions finish a hook at the same moment while the file is over its limit. Expected: the file still parses, at most one line is lost, no `.timing.tmp*` file stays. Test: Task 2, `a cut that loses the race leaves the file as it was`.
2. `.timing` cannot be written: it is a folder, the projects root is missing, the disk is read-only. Expected: every hook prints and exits as with timing off, and no folder is created. Test: Task 3, `a root that takes no file`.
3. A hook input whose event name is not a name: a path, 10,000 characters, an object, missing. Expected: `e` is `?` and nothing else of the input reaches the file. Test: Task 3, `no text reaches the file`.
4. A CI machine that is slow or noisy for one run. Expected: `--check` measures a failing case once more and fails only when it fails twice, and its message names the case, its median, the empty script's median and the limit. Test: Task 8, `one slow measurement is not a failure`.
5. A conversation file of several hundred MB, with a broken last line or lines that are not JSON. Expected: `--live` reads it as a stream, skips those lines, and prints no part of a command. Test: Task 1, `a broken line is skipped` and `a command is never printed`.

## Pull request B: timing lines (branch `1.5.4-timing`, on A)

### Task 2: `timing.mjs`

**Files:**
- Create: `timing.mjs`, `timing.test.mjs`
- Modify: `bench.mjs`, `live-times.mjs` (import `pct` from `timing.mjs`)

**Interfaces:**
- Produces, all in `timing.mjs`:
  - `export const FILE = '.timing'`, `export const MAX = 256 * 1024`
  - `export function begin(hook)`: starts a run. Takes `'save' | 'brief' | 'enforce' | 'gate'`. Any other value, or `process.env.PROJECT_MEMORY_TIMING === '0'`, starts nothing, and then `tag`, `mark` and `flush` do nothing.
  - `export function tag(event, detail)`: sets `e`. `event` is kept when it matches `/^[A-Za-z]{1,24}$/`, else `'?'`. `detail` is added as `:detail` when it matches `/^[a-z]{1,12}$/`, else left out.
  - `export function mark(phase)`: adds the milliseconds since the last `mark` (or `begin`) to `p[phase]`. Called twice with one name, the two times add up.
  - `export async function flush()`: appends the line, clears the run. Never throws, prints nothing, creates no folder.
  - `export function read(since, file)`: the lines of `file` with `t >= since`, oldest first, as objects. Skips a line that does not parse or whose `t` or `ms` is not a number. Keeps keys it does not know. A missing file gives an empty list. The caller passes the path (`join(projectsRoot(), FILE)`): `doctor` and the bench both have `projectsRoot`, and `read` stays synchronous.
  - `export const pct` (from Task 1) and `export const stats = (ms)` returning `{ runs, median, p90, worst }` of an unsorted list.

The cut, the one algorithm here, is the `.stop-ran` pattern of `memory-tier.mjs:733-739` with other numbers:

```js
appendFileSync(file, line + '\n', { mode: 0o600 });
const size = statSync(file).size, tmp = `${file}.tmp${process.pid}`;
if (size > MAX) {
  try {
    const lines = readFileSync(file, 'utf8').split('\n').filter(Boolean);
    writeFileSync(tmp, lines.slice(Math.ceil(lines.length / 2)).join('\n') + '\n', { mode: 0o600 });
    if (statSync(file).size === size) renameSync(tmp, file);   // another run appended meanwhile: keep the file, cut next time
  } finally { rmSync(tmp, { force: true }); }
}
```
